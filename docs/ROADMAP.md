# FullVision: what it needs to be worth paying for

Written 2026-10-17. Follows the Schoology/Teams comparison (2026-10-17).

FullVision won't win by matching Schoology or Teams feature for feature. Both are free to a teacher and already approved by the district. It wins by being the tool that writes BC reports better than anything else, with the student work behind them in the same place: students send it, the teacher grades and returns it, and it lands on the report. Everything below either removes a reason not to pay, or makes that work much better.

## 1. Remove the reasons not to pay

Without these, no feature set will be worth paying for.

1. **Roster import from MyEducation BC.** Schoology and Teams get rosters automatically. A teacher typing 150 students by hand will quit on day one. Accept MyEd BC's class-list export as is: map its columns, match on student number, and add students who are already in another class without making duplicate records. Done 2026-10-22 (#312): the Students tab's import review matches on student number, then name.
2. **Reporting periods.** Done 2026-10-17 (`docs/DECISIONS.md`, "Reporting periods"): up to six dated terms per class in Class Settings, and reports that follow Report N. Since 2026-11-03 a report's grade is the year to date as of its term's end, and the gradebook, dashboard and student pages have no term picker: they show the year so far. The mobile grade filter uses the class's reporting terms (commit 8caf06a4).
3. **Safe student handling.** Districts and parents will ask "what happens to my child's record?" Done 2026-10-19 (`docs/DECISIONS.md`): removing a student withdraws them, with a Withdrawn list, Re-enrol and a permanent delete as a second step. Still to do: Restore for deleted classes.
4. **Rolling over to next year.** Duplicate Class copies the class settings, categories and weights, learning map and sentence starters, but not reporting terms, rubrics or assessments (2026-10-18). Assessments (2026-10-18), rubrics (Rubric Bank, 2026-10-18) and the grading setup ("Copy grading setup…", Teams' Import settings, 2026-10-18) can each be copied to another class.
5. **Trust basics:** closed signup or SSO, a real privacy page, and full data export. A teacher paying personally needs to know they can leave with their data. Privacy page done 2026-10-14 (#135); Download Class Backup in Class Settings done 2026-10-22 (#325); Restore Class from Backup done 2026-11-01. Still to do: closed signup or SSO, and an export of everything at once.
6. **The first ten minutes:** bigger type, a legend for every code (CRT, QAP, NS…), phones sent to the mobile app, and three first-run tips. If the app feels hard on day one, no price will feel worth it.

7. **One class on two computers.** A teacher's settings must be the same on the computer at school and the one at home. Done 2026-11-10 (`docs/DECISIONS.md`, "Class settings on two computers"): a save sends only the setting that changed, a class load takes every setting from the server, and a whole list of categories is checked against the server before it is saved. Still to do:
   - Display choices kept on one device (`gb_newestFirst`, the roster's sort, the report's paper size and the like) move to the server, so they follow the teacher.
   - Teacher preferences (`save_teacher_preferences`) are still sent as one whole copy, so an old tab can put an old one back; send only what changed, as class settings now do. Built Nov 24, not applied (`migrations/2026112404_teacher_preferences_patch.sql`): a save sends only the preferences that changed to `patch_teacher_preferences`, which merges `dashboard_prefs` key by key. The migration must be applied before the app change merges. `save_teacher_preferences` stays for the released app and its waiting saves.
   - The database checks a category save itself (the list's version goes up with it and an old one is refused), so the check does not rest on the browser reading the list first.
   - Category edits kept on a computer when a save could not be made (`gb-category-draft-<class>`) go, without a word, with that class's saved copy: at the 14-day purge of saved copies, or when the browser clears its storage. Keep them, or say so, separately from the saved copy.
   - "Other changes from this computer are still being sent… Save again in a moment." is not true when the sign-in has expired or another tab holds the outbox: then those changes wait until the teacher signs in again or the other tab sends them. Say so for those two cases.

8. **Student cards a copied database cannot open.** Decided 2026-11-10 (`docs/DECISIONS.md`, "Card codes the database cannot read"): the database keeps only keyed fingerprints of a card's code and password, made with a key held outside it. Built in slice S3 of `docs/plans/student-page-build-plan.md`; slips moved to the card key in `S3-S1` (PR 1150), built and deployed, release pending. Still to do after that:
   - The key for hashing a student's network address falls back to the database's own address when `STUDENT_SUBMIT_IP_KEY` is not set. Then anyone holding that address could turn the 30-day log's hashes back into network addresses. Colin set the key on Nov 10 (`DECISIONS.md`, "What was applied and deployed that night"); the fallback is removed in code (Nov 24): without the key every route answers a server error and logs `no_ip_key`. Deployed Nov 24.
   - Show a count of unknown card codes on the support report, so a run of guesses is seen. The per-address limit alone wears thin at province scale.
   - Give the edge functions a database login that can run only the `student_submit` functions. Today both sign in as the database's owner, so a bug in a function has every right. Soon: S3 adds a second such function. Built Nov 24 (`migrations/2026112402_edge_function_logins.sql`, applied Nov 24): `fv_student_submit` and `fv_teacher_cards`, each able to run only its function's calls, read from `STUDENT_SUBMIT_DB_URL` and `TEACHER_CARDS_DB_URL` with no fallback. Done Nov 24: Colin set the passwords and secrets, both functions were deployed from `main`, and each was seen signed in as its own login (a page read for `student-submit`, a card made for `teacher-cards`). Left: the platform's `net` grant to every role, which only Supabase can take back.
   - Hash a student's session token in the edge function, not in the database. Today the token crosses to the database in the clear on every page read; someone watching the database live could catch one (it ends at midnight). Done Nov 24 (`migrations/2026112401_session_token_hashed_in_function.sql`, applied, and `student-submit` deployed a minute later): the function sends only the token's hash and makes a new session's token itself. A slip's token the same way: built Nov 24 (`migrations/2026112403_slip_token_hashed_in_function.sql`), with the function's old path for the database before `2026111160` removed; applied and deployed Nov 24, a minute apart.
   - Backups taken before the card migration hold its 30 old codes. They are dead, but restoring such a backup would bring back the old readable design.
   - One Supabase account holds both the database and the key, so two-step sign-in on that account matters more than anything in the card design.
   - A Yes on Print New Card or New Codes for This Class waits while the card list is being read. If that read never answers, the screen shows no word while it waits. Show one ("Making cards…"). Done 2026-11-11 (PR 1040).
   - A card marked Printed on one computer whose Printed mark has not reached the server yet shows Not Printed on another computer until it does. The computer that printed it keeps a note and sends the mark again the first time it reads the list after a reload (PR 1014).

9. **Tied pieces on a report after a returned grade is cleared.** When a returned grade is cleared, its entry moves to the end of the student's returned grades, so a report can name two tied pieces the other way round ("Lowest work: A and B" becomes "B and A"; no number moves). The fix: the report orders tied pieces by `calc.js`'s own rule, so the order no longer rests on where the entry is stored. Its own pull request (PR 1004, review point 5). Best work and Lowest work ties were put in `calc.js`'s order on Nov 12 (PR 1326). The one place still in stored order was the Learning Outcomes block's list of pieces under each competency; built Nov 24 (`fix/report-tie-order`): it lists them in the order they count in (`calc.js` `inCountingOrder`: by date, then the same-date rule), so a cleared grade moves no piece. No grade changes; in Demo Mode 405 of 729 Learning Outcomes lines now read in date order. Waits for Colin's review.

## 2. Make the core job far better than anyone else

1. **Write comments from the evidence.** FullVision already has everything a comment needs: proficiency by competency, observations, the questionnaire answers, goals and reflections. Done 2026-10-28 (`DECISIONS.md` 14; `questionnaire-plan.md`): the Term Questionnaire shows that evidence beside a Comment Bank in BC's four parts, each sentence filled in for the student and offered only when its data exists. Generate assembles a draft from the bank's sentences (no model writes text); the teacher edits and approves the comment. TeacherDashboard and Almanack start from nothing; FullVision starts from what happened in class. At a Glance, the Observations card and drawer, and the pinned Teacher Comment done 2026-11-03 (`DECISIONS.md` 18–21). Still to do: the Focus Area pick is kept per device (no server column yet).
2. **Reports that fit the sheet.** One form per class, fixed and flowing blocks, Letter or Legal, a return strip, an issued copy to reprint or send. Decided 2026-10-20 (`DECISIONS.md`, "Report forms"); plan in `report-forms-plan.md`. Since 2026-11-13 Progress Reports is One Report for every teacher (`DECISIONS.md`, "One Report"; plan in `plans/one-report-build-plan.md`): one list of parts with switches in print order, four Setups, parts that flow from page to page, rows left off and headings renamed on the page, the Teacher Comment edited where it prints, reworded questions per class, changes for the class or one student, and a printed copy that reprints as it went home. Page Studio and the Quick Report / Custom choice are gone. Still to do, each its own change: Excuse It Instead on a missing piece (it changes a grade: Colin's review); IEP Goals for one student; Use in My Other Classes; a long Teacher Comment split across pages; rows are left off by their printed name, so two rows with the same name are left off together.
3. **Output shaped for MyEd BC.** Teachers end up pasting into MyEd anyway. Give them a per-class export of each student's proficiency level and comment, laid out the way they'll enter it, so they don't retype anything.
4. **Student self-assessment and goal-setting without student accounts.** BC reporting expects student self-assessment of the core competencies and goal-setting. The `goal` and `reflection` tables already exist. Add a per-class link or QR code where students answer a short form, and have the answers land in the report. Neither Schoology nor Teams does this the BC way. Done: Questionnaires with printable QR slips (#399, 2026-10-25) and the student page (`s/`); the Self-Assessment and Goal report blocks (#462, 2026-10-28).
5. **An evidence trail for every level.** "Why is this a 3?" One click should show the scores, observations and work samples behind it, and let the teacher attach a photo of student work. Partly done: the evidence drawer on the student page's competency card (#224, 2026-10-19). Still to do: attaching a photo. This is what a teacher shows a parent at conferences, and what an admin wants if a grade is challenged.
6. **Fast in-class capture on the phone:** tap a student, pick a competency, speak or type one line, done. Observations are already the app's best screen. Making them two seconds to record on a phone is what makes the evidence trail real.
7. **Reporting for students on IEPs.** Designations are already on the roster. Let a teacher report a student against their IEP goals instead of the course competencies, with the right wording on the report. No mainstream tool handles this well, and resource and inclusion teachers would buy for it alone.
8. **The BC curriculum, exactly as the Ministry wrote it.** Done 2026-11-02 (`DECISIONS.md`, "The BC curriculum bank"): every grade 8–12 course except second languages, copied word for word from the Ministry's files, with Ministry folders, readable codes and I Can statements for all 5,029 competencies, and a New Class wizard that shows the wording before import. Still to do: the Province's written permission to reproduce the text (requested), a field test of the I Can statements with a few ELA and SS teachers, a re-fetch each June, showing Big Ideas and Content, and retiring the old bank's shape once classes have moved.
9. **Paper work for a whole class, added in minutes.** A teacher scans a pile on the school photocopier and adds each student's pages from one page on a computer. Decided 2026-11-17 (`DECISIONS.md`, "Add Work for the Class"); plan in `plans/add-work-for-class-plan.md`. Built 2026-11-17 and on `main`, slices B1 to B7: the page with one file per student; Split the Scan (up to 150 pages, blank backs left out, names typed, a page moved between pieces, Turn Every Page, Set Up Like Last Time); files or a folder matched by name with a Waiting tray; sticker sheets printed from Class Settings, with their codes in the database (migration `2026111710`, applied); Grade in Scan Order; one pile for two classes and a late paper's own assessment; Split a Scan on the phone. A sticker on a paper's first page names its piece when the scan is split (PR 1541). Offered in every class, student page or not (PR 1544). Still to do: a check in a signed-in class and with a real copier scan; a sticker on a page scanned on the school copier before a class set is printed (one sticker to a page, as a paper carries: a whole sheet of 80 does not read). Not built: the answer key (cancelled by Colin, Nov 17), the scan shared straight from an Android phone's mail (built, then taken out: the share can reach the network before the app's handler is active), and finding upside-down pages from the picture alone (the trial made wrong calls).
10. **A calmer Dashboard.** Teachers called it "overwhelming". The top bar and the student cards stay as they are; the row between them becomes an Inbox of the work that has come in (two thirds) and one Competencies tile (one third), sized so the cards start below the first view. Decided 2026-11-17 (`DECISIONS.md`, "The Dashboard's middle row"); plan in `plans/dashboard-inbox-plan.md`. Done on `main` 2026-11-18 (D1 to D9, on by default), not released; the Bulletins tile under the Inbox comes with Bulletins. No database change.
11. **Bulletins.** A one-way class feed: the teacher posts, students read it on the first tab of their page, and the teacher sees who has seen it; Quick Polls and a Whiteboard open on the classroom TV; the teacher can post from the phone, a photo of the board included. Decided 2026-11-17 (`DECISIONS.md`, "Bulletins"); plan in `plans/bulletins-plan.md`. Stage 1 (bulletins, Seen and reactions) is on on `main` since 2026-11-18 (B1g), not released: the teacher's page, the Dashboard tile, the phone app and the student's first tab, with the privacy page, a Bulletins sheet in Download All My Data and a help article. Next is stage 2, Quick Polls and the TV Screen. Four stages, five small migrations, each shown to Colin before it is applied. The order of the three builds is in `plans/quizzes-plan.md`, "Order across the three plans".
12. **Quizzes.** A teacher writes a quiz on an assessment, each question tagged to one of its competencies; students answer on their own page; the teacher confirms a suggested level for each competency before anything counts. Decided 2026-11-17 (`DECISIONS.md`, "Quizzes"); plan in `plans/quizzes-plan.md`. Not built. Three small migrations; the slice that turns a quiz into grades goes to Colin's review.

## 3. Bring teachers over from the district tools

1. **Import scores from Teams, Google Classroom and Schoology.** There's already an unused `import_teams_class` RPC. Teachers who still assign there can bring their scores in on day one and move their assignments over when they're ready. That turns your strongest competitor into a source of data instead of a reason to stay.

## 4. What the school tier needs

- **Co-teachers and shared classes:** resource teachers, EAs and TOCs, with view-only and edit roles.
- **A principal view:** which classes have finished their Learning Updates, and how far along each teacher is. Admins pay for visibility.
- **School-wide templates:** shared comment banks, a common questionnaire, the same category setup across a department.

## 5. Cut or hide

Six calculation methods, the per-assessment weight, the decay slider, and several settings that are only explanation text are confusing for most teachers. Default them sensibly (Most Recent for grades K–9, Mean for 10–12) and put the rest behind "Advanced." Showing less makes the app look more powerful.

## Order of work

1. **This term:** MyEd roster import (done), withdraw instead of delete (done), legibility pass, closed signup.
2. **Before the next reporting round:** reporting periods (done), plus drafted comments from evidence (done) with the MyEd-shaped export.
3. **Over the next few months:** student self-assessment link (done), the evidence trail (partly done), phone capture, IEP reporting.
4. **When a school asks:** co-teachers, the principal view and templates.

## How to know it's worth the money

Time it. Have three colleagues write one round of Learning Updates in FullVision and in their current tool. If FullVision saves each of them several hours, that time saving is the line to lead with.
